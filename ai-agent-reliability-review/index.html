AI Agent Workflow Reliability Review

Verify what your AI agent actually did, not just what it says it did.

An agent can report “done” while the application behind it holds the wrong value, a duplicate charge from a retry, or an operation that never finished. This review checks the workflow against the application's own state: what changed, what must not have changed, and whether background work had settled before anyone called it a success.

01 · The problem

A finished tool call is not a finished job

Most agent evaluations read the agent's own answer or the last screen it saw. The failures that cost money happen in the database, the queue and the systems downstream.

False success

The agent says the task is complete; the record it was meant to change is unchanged or wrong.

Retry duplicates

A retry repeats the side effect, not just the request: two payments, two emails, two orders.

Wrong state

The operation runs, but leaves incomplete or incorrect values behind, or touches another tenant's data.

Unsettled work

Queue jobs are still running when the run is judged a success, so their effects are never checked.

Broken business rules

Every step looks fine on its own, yet the outcome breaks a rule the business depends on, such as one payment per invoice.

02 · The project behind it

AssertState: judge the outcome, not the claim

Open source · Apache-2.0

AssertState

A deterministic acceptance-testing harness for browser and AI agent workflows. It decides pass or fail from independent, read-only reads of the application's own state, never from the agent's completion message.

  • Contracts that state the expected final state
  • Read-only database verification, with the read-only role checked at run time
  • Forbidden side-effect policies, such as at most one new payment per invoice
  • Queue settlement: background jobs are drained before the verdict
  • Repeated trials with per-run evidence you can reproduce
View on GitHub ↗
The core idea

The agent can't see or write the evidence that judges it. The verdict comes from the application's data, read through a role that cannot change anything.

forbid what must not happen.

03 · Demonstration results

Same “done”, different outcome

One simulated invoice: bill-december for tenant acme, USD 98.70. The simulated agent reports DONE in both scenarios. The only difference is a second payment job for the same invoice, queued 0.5 seconds later.

The payment row exists with status paid and amount exactly 98.70. No forbidden side effect fired: one payment, one tenant.

One-sided 95% Wilson lower bound 0.5258 against a 0.50 threshold. Three trials prove the test path, not a reliability rate.

trials rejected

The status and amount checks still passed, and the agent still said DONE. But after the queue drained, a second payment row existed for the same invoice, and the “at most one new payment” rule fired in every trial.

Root cause in the fixture: an idempotency key is stored but not enforced by a uniqueness constraint.

Expected state answers “did the right thing end up true?” Forbidden side effects answer “did anything happen that must not?” A check of the final row alone passes the slow-retry run. Only the settled before/after change shows the extra payment.

In a real payment integration, the same pattern could mean a duplicate charge. Here it produced simulated database rows only.

05 · Scope

What this sample does not prove

Demonstrated
  • A test adapter can report DONE for both a clean run and a duplicate one
  • Final PostgreSQL state can be read through a separately verified read-only role
  • A contract can tell one valid payment apart from a forbidden duplicate, after queue settlement
Not demonstrated
  • No live language model or browser agent: the adapter is a deterministic demo adapter
  • No real payment gateway, bank or card network was called; no real payment was made
  • No production data, real workload, authorization model or customer environment
  • Three trials per scenario show the test path works; they are not a reliability estimate for any AI agent
